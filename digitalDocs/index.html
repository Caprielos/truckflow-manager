2. Architecture Rules

TruckFlow follows a simplified but rigorous Domain-Driven Design approach. The current focus is the pure domain model, without application workflows, persistence, REST APIs or external integrations.

The domain must model business concepts first. Technical mechanisms such as database access, HTTP controllers, file storage and external services belong to later layers.

Layer separation

  • domain contains business concepts, invariants, value objects, entities and aggregate roots.
  • application will orchestrate use cases and ports.
  • infrastructure will connect the system to memory repositories, databases, files and external systems.
  • api will expose the application behavior to clients.

Allowed cross-domain references

A domain must not import full aggregate roots from another domain. References across contexts are allowed only through stable identifiers, stable value objects or abstract references. 

Allowed:   ShipmentItem -> CargoId
Allowed:   ShipmentLeg  -> LocationId
Avoid:     ShipmentItem -> CargoUnit
Avoid:     ShipmentLeg  -> Location

3. Domain Packages

The current domain foundation is composed of ten main packages. Each package owns a clear part of the business vocabulary and must keep its boundaries explicit.

domain.users

Models application accounts, profile data, roles, permissions, user status and user preferences. A User is not the same concept as an operational worker such as a driver.

domain.qualifications

Provides the static catalog of qualifications, driving licenses, CQC, ADR and other operational certifications. A Qualification is a catalog entry, not a personal document or expiration record.

domain.operational

Models real operational company figures such as Driver, Mechanic, WarehouseOperator, Dispatcher and Manager.

domain.vehicles

Models fleet units, body profiles, technical specifications, coupling profiles, operational capabilities and vehicle combinations. The core distinction is between VehicleUnit and VehicleCombination.

domain.cargo

Models merchandise as a reusable domain concept. A CargoUnit declares cargo properties, packaging, temperature, hazard and transport requirements, but does not assign vehicles.

domain.locations

Models reusable logistics places such as depots, warehouses, customers, suppliers, yards, hubs, ports, airports and terminals. A Location is shared by shipments, trip templates and future operational modules.

domain.triptemplates

Models abstract route patterns and technical mission templates. A TripTemplate is not a real executed trip and does not contain drivers, vehicles, cargo, real times or GPS tracking.

domain.shipments

Models shipment requests: what must be shipped, which cargo items are included, which logical legs are needed, which service level applies and which transport requirements are declared. A Shipment is not transport execution.

domain.documents

Models a Document as a pure business concept with identity, code, type, category, status, metadata, logical content and abstract references. It does not manage physical files, upload, storage or signatures.

domain.compliance

Models abstract compliance requirements. A ComplianceRequirement describes rules, categories, obligation levels, severity, targets, sources and jurisdictions, but does not execute compliance checks or create violations.

4. Domain Review Corrections

The first concrete domain review strengthened the foundation without introducing new operational features. The goal was to make the pure model safer, clearer and easier to consume from the future application layer.

1

Validate before mutating aggregates

Aggregate methods now validate all new values before assigning internal state. This prevents partially modified objects when an invariant fails.

2

Use custom exceptions in simple domains

Smaller domains such as documents, compliance, locations and trip templates now use explicit domain exceptions instead of generic Java exceptions.

3

Use custom exceptions in complex domains

Cargo, shipments, vehicles, operational and users now expose clearer error types, improving testability and future application error handling.

4

Make OperationalCode mandatory

OperationalCode is now consistent with other business codes such as FleetCode, ShipmentCode and DocumentCode.

5

Make qualification catalog tests less fragile

Qualification catalog tests focus on behavior, metadata completeness and code uniqueness instead of rigid item counts.

6

Clean local IDE and generated files

Local IDE files, Maven build output, macOS generated files and temporary script or patch files are documented as non-source artifacts and excluded from versioning.

5. Domain Exceptions

Domain-specific exceptions make validation failures explicit and easier to handle later in the application layer. They are part of the domain language and should represent real violations of the pure model.

Shared base exceptions

it.gabriele.truckflow.domain.shared.exceptions
├── DomainException
├── DomainValidationException
└── InvariantViolationException

Domain-specific examples

InvalidUserException
InvalidCargoException
InvalidShipmentException
InvalidDocumentException
InvalidComplianceRequirementException

ComplianceViolationException is intentionally not part of the current pure domain because concrete compliance checks, results, violations and audit records have not been modeled yet.

6. Glossary

This glossary keeps the English technical vocabulary aligned with the code while exposing Italian explanations through the same tooltip system.

Aggregate Root

The main consistency boundary of a domain aggregate.

Value Object

An immutable domain concept defined by its value rather than identity.

Invariant

A rule that must always remain true for the domain object to be valid.

Bounded Context

A clear business boundary with its own language, rules and model.

Abstract Reference

A lightweight reference to another context without importing its aggregate root.

Application Layer

The layer that will orchestrate use cases without owning pure domain rules.
